# Bad Case 分析与方法论

> 记录真实遇到的失败案例、定位过程、以及从中提炼的方法。
> **所有案例均有日志或数据佐证，不是推测。**
> 日期：2026-10-01

---

## 一、为什么单独写这份文档

面试里说"我们效果不错"没有任何信息量。**能讲清楚"哪里会错、为什么错、怎么发现的、怎么防"才是真本事。**

更重要的是：这份文档里的 **4 个案例中有 2 个，问题根本不在系统，而在"我们用来衡量系统的指标"本身**。
这个认知是踩了坑才拿到的。

---

## 二、Bad Case 分类（按链路层）

| 层 | 典型失败 | 表现 | 我们的实例 |
| --- | --- | --- | --- |
| **度量** | 指标算错了 | 指标异常但系统正常 | 案例 1 ★ |
| **配置** | 参数与模型不匹配 | 指标下降 | 案例 2 |
| **检索** | 该找的没找到 | 检索指标低 | （未发现） |
| **排序** | 找到了但排太后 | 召回了但没进 Top-K | （未发现） |
| **生成** | 找到了但答错/答偏 | 检索正常、答案错 | 案例 3 |
| **工具** | 动作执行错目标 | 操作结果不符预期 | 案例 4 |
| **拒答** | 该说"不知道"却编造 | 知识库未覆盖仍作答 | **未系统测过** |

> 注意最后一行：**"拒答能力"是我们明确的评测盲区**。当前评测集里没有"知识库未覆盖"类问题，
> 所以无法衡量模型会不会编造。这是下一步要补的。

## 三、案例 1：评测指标全 0，但系统其实完全答对了 ★★★

### 现象

自建评测集跑完，32 题中 31 题检索指标满分，**1 题全项 0 分**：

```
metric: &{{0 0 0 0 0 0} {bleu1 0.1395 ... rouge1 0.2273 ... rougel 0.1818}}
         └─ 检索：完全没找到   └─ 生成：部分重叠
```

### 第一直觉（错的）

"这题检索失败了，一条相关内容都没找到。"

### 关键动作：不满足于直觉，去看实际输出

**第一步——看模型当时的回答**（不是只看分数）：

> 私有云版（Private Cloud）的计费方式是一次性授权。这意味着用户需要支付一笔固定的费用来获取私有云版的服务，
> 而不是按使用量或时间订阅。**具体的报价需要根据实际情况进行评估，通常起价为 30 万元。**
> `<kb doc="..." chunk_id="..." kb_id="..." />`

而参考答案是：「私有云版是一次性授权计费，报价需评估，通常 30 万元起。」

**答案完全正确，还带了引用。**

**第二步——如果真的一条都没检索到，模型不会答出这些细节。** 所以：检索成功了，生成也成功了，
**是评测的"命中判定"出了问题。**

### 根因

评测框架把"检索到的分块"映射回"标注的段落 ID"，用的是**字符完全包含**匹配：

```go
// internal/application/service/metric_hook.go
for i, passage := range qaPair.Passages {
    if strings.Contains(passage, r.Content) || strings.Contains(r.Content, passage) {
        pid := qaPair.PIDs[i]
        retrievalIDs = append(retrievalIDs, pid)
        break
    }
}
```

**只要检索回来的分块与标注段落不是严格的子串关系，这题就被判为"零命中"**——哪怕内容完全正确。

失效场景包括：分块器改写格式（`标题：正文` → `## 标题\n\n正文`，冒号变标题）、
分块合并、文本归一化（全角/半角、空白符折叠）等。

### 我在真实知识库上复现了这个机制

把同一份语料灌进一个独立知识库，问同样的问题：

```
检索到 1 条引用（1457 字）:
  # 知微 WorkMate 产品与售后政策 ⏎ ⏎ ## 社区版（Community） ⏎ ⏎ 免费，支持 1 个知识库...

标注段落（P3）能否在引用里找到？
  包含匹配: ❌ 匹配失败 → 该题会被判 0 分
```

**引用的内容里明明包含正确答案**（"私有云版（Private Cloud）..."），但格式被改写后
**包含匹配失效**。

### 结论与影响

| | |
| --- | --- |
| 系统实际表现 | ✅ 检索正确、生成正确、引用正确 |
| 评测记录 | ❌ 检索全项 0 分 |
| 性质 | **评测框架的假阴性（false negative）** |

**如果不查这一步，会得出完全错误的结论**："我们的检索在某类问题上会完全失效"——
进而去做无用的检索优化。

### 教训

> **1. 评测框架本身也需要被验证。** 它是代码，代码就有 bug。用它下结论之前，先确认它测的是真问题。
> **2. 指标异常时，第一件事是去看原始输出**（模型的回答、检索到的内容），而不是指标本身。
> **3. 自动评测 + 人工抽检必须结合。** 纯自动指标既会漏报也会误报——
> 这个案例就是典型的误报，只有人工看一眼回答才能发现。

### 待办

- [ ] 修正评测框架的匹配逻辑（用分块溯源 ID 或模糊匹配替代严格子串包含）
- [ ] 在评测报告里把该题的分数标注为"假阴性，实际正确"

## 四、案例 2：重排阈值把正确答案滤掉了（指标下降，真问题）

### 现象

开启重排后，检索 precision 从 1.0 掉到 **0.9688**，生成指标同步下降。
直觉结论："重排不但没用还有害。"

### 定位过程

**第一步——看重排的实际打分**：

```
rank=1 score= 6.6088   ← 正确段落
rank=2 score=-0.9100
rank=3 score=-0.9803
```

**重排工作得极好**，正确段落断崖式领先。问题不在模型能力。

**第二步——看过滤阶段**：

```
stage=Rerank action=threshold threshold=0.3
stage=Rerank action=output    filtered_cnt=1     ← 21 个候选只剩 1 条
```

### 根因

`bge-reranker-v2-m3` 输出的是**原始 logits（约 -10 ~ +10）**，而默认阈值 `0.3` 是按
**0~1 归一化分数**设计的。用 0.3 去卡 logits，等价于"只保留排名第一且分数为正的那条"。

### 修法与效果

把阈值从 `0.3` 改为 `-10`（保留全部候选，只让重排决定顺序）：

| 配置 | 检索指标 | rouge-1 |
| --- | --- | --- |
| 重排，阈值 0.3 | 0.9688 | 0.4281 |
| 无重排 | 1.0000 | 0.4897 |
| **重排，阈值 -10** | **1.0000** | **0.5070** |

### 教训

> **换重排模型必须重新校准阈值——不同模型的分数尺度完全不同。**
> 有的输出 0~1 相似度，有的输出原始 logits，拿同一套阈值套不同模型必然出事。

## 五、案例 3：7B 模型读错输出列名（生成层）

### 现象

让它查"内存占用最高的 3 个进程"，它执行的命令是**正确的**：

```powershell
Get-Process | Sort-Object -Property WS -Descending | Select-Object -First 3
                                    ↑ WS = Working Set = 内存，命令没错
```

但汇报时说成了"占用 2.55% 的 **CPU**"——**把内存数值说成了 CPU**。

### 定位

命令对、结果对，**错在"读结果"这一步**。小型模型在把表格型输出转成自然语言时，
容易只看数值不看列名。

### 修法

在系统提示词里显式约束：

```
汇报数据时必须看清列名：内存是 Working Set(WS) 或 PrivateMemorySize，
CPU 是 CPU 列，不要把 CPU 占用说成内存占用。不确定列的含义就先把列名一起列出来。
```

修完后重测：正确报出"实际内存 827,867,136 字节 / 482,381,824 字节 / 265,322,496 字节"。

### 教训

> 这是**模型能力边界**，只能缓解不能根除。7B 模型适合单步和 2-3 步任务，
> 涉及"精确读取结构化输出"时要靠提示词约束 + 结果校验。

## 六、案例 4：Agent 生成了错误的文件路径（工具层）

### 现象

在个人 Agent 场景里，让它删除 `agent.log`，它生成的命令是：

```powershell
Remove-Item -Path "C:\knowence\agent.log" -Force
```

而**实际文件在 `C:\knowence\agent\agent.log`**——路径少了一级。

### 结果

**被分级审批层拦下了**。用户看到命令后点了"拒绝"，文件完好无损。

### 教训

> **这是"为什么 Agent 必须有审批层"最有说服力的证据**——不是理论风险，
> 是模型真的会生成错误路径，而错误路径上的删除操作是不可逆的。
> 人眼扫一眼命令就能发现，这是最便宜也最有效的防线。

## 七、从这些案例提炼的方法论

### 7.1 归因顺序：从度量开始，而不是从模型开始

指标不对时，按这个顺序排查：

```
① 度量本身对不对？   ← 最容易忽略，我们踩了两次
      ↓
② 配置对不对？       ← 阈值、参数、模型绑定
      ↓
③ 检索找对了吗？     ← 看召回的原始内容
      ↓
④ 排序合理吗？       ← 看打分分布
      ↓
⑤ 生成答对了吗？     ← 看实际回答
```

**案例 1 和案例 2 的问题都在 ① 和 ②，如果一头扎进 ③④⑤ 就会白费力气甚至做错决策。**

### 7.2 三条硬经验

| 经验 | 来自 |
| --- | --- |
| **指标是信号不是结论**——异常时回看链路中间输出 | 案例 2 |
| **评测框架本身也要验证**——它也会错 | 案例 1 |
| **自动指标 + 人工抽检必须结合**——纯自动既漏报也误报 | 案例 1 |

### 7.3 Bad Case 库怎么建

1. **每条 bad case 记录**：问题、预期、实际、指标、日志片段、归因层、状态
2. **定期回归**：修过的 bad case 要进回归集，防止改一处坏一处
3. **区分"系统错"与"度量错"**：这两类的处理方式完全不同——前者改系统，后者改评测

### 7.4 我们目前的评测盲区（如实说明）

| 盲区 | 风险 |
| --- | --- |
| 无"知识库未覆盖"类问题 | **无法衡量模型会不会编造**（拒答能力未测） |
| 无多跳问题 | 跨段落推理能力未测 |
| 单标注、无一致性校验 | 标注口径本身可能有争议 |
| 语料仅 20 段 | 生产规模（万级分块）表现未知 |
| BLEU/ROUGE 只是字面重合 | **不能证明没有幻觉** |

## 八、面试怎么用这些案例

**推荐讲案例 1**，因为它最能体现判断力：

> "评测跑出来有一题检索全 0 分。第一反应是检索失败了，但我去看模型的实际回答——
> 答案完全正确，连引用都对。所以我去查评测框架，发现它用『字符完全包含』把检索到的分块
> 映射回标注段落，而分块器会改写格式（比如把『标题：正文』拆成『## 标题 + 换行』），
> 导致包含匹配失效，把一次成功的检索误判成了零命中。
> **这件事让我形成了一个习惯：用评测下结论之前，先验证评测本身。**"

**案例 2 配合讲**，能形成"指标不等于真相"的完整主题：

> "另一次是开了重排指标反而降。同样是先看中间输出——重排给正确段落打了 6.6 分、
> 无关的 -0.9 分，排序明明是对的。最后定位到阈值：这个重排模型输出的是原始 logits，
> 而默认阈值是按归一化分数设的。改一个数字，检索回满分、生成还涨了 18%。"

**两个案例合起来传递一个信号**：**这个人不容易被表面数字骗。**
面试官最怕招到"给个数就信"的人，这两个案例恰好证明不是。
