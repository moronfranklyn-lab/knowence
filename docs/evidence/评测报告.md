# RAG 效果评测报告

> 评测对象：知微 Knowence 检索与生成链路（全本地模型）
> 日期：2026-10-01　｜　数据集版本：`knowence-policy-v1`
> **所有数字均为本机实测，可按下文步骤复现。**

---

## 一、为什么做这个评测

平台自带评测框架（检索侧 Precision / Recall / NDCG@3 / NDCG@10 / MRR / MAP，生成侧 BLEU / ROUGE），
但**框架自带的数据集只有 1 条 QA**，统计上无意义，也无法区分不同配置的优劣。

于是自建了一份评测集：**以一份 20 段落的政策文档为语料，配 32 道有明确答案的问题**，
每题标注对应段落（qrels），用于计算检索指标；同时提供参考答案，用于计算生成指标。

---

## 二、评测集设计

| 项 | 值 |
| --- | --- |
| 语料段落 | **20 段**（产品定价 / 退款政策 / SLA / 数据合规 / 部署要求 / 迁移 / 培训 / 发票 / 灾备 / SSO / API 配额 / 升级政策 / 试用 / 数据导出） |
| 评测问题 | **32 题** |
| 相关性标注 | 每题 1 个正例段落（qrels），共 32 条 |
| 参考答案 | 32 条 |

**设计要点**：语料刻意包含**主题相邻的干扰段落**——例如"私有云版"同时出现在定价、退款、SLA、部署、灾备、SSO、升级等多个段落中，
使得检索必须区分"提到该主题"与"回答该问题"，而不是简单命中关键词。

数据集与生成脚本见本目录 `dataset/` 与 `make_eval_dataset.py`。

## 三、被测配置

三个模型全部本地部署，无任何云端调用：

| 环节 | 模型 | 部署位置 |
| --- | --- | --- |
| 向量化 | `bge-m3-FP16`（1024 维） | 本地 llama.cpp |
| 重排 | `bge-reranker-v2-m3-FP16` | 本地 llama.cpp（`--rerank`） |
| 生成 | `Qwen2.5-7B-Instruct Q4_K_M` | Windows RTX 4060（Ollama） |

检索参数：`embedding_top_k=30`、`vector_threshold=0.2`、`keyword_threshold=0.3`、`rerank_top_k=30`。

## 四、实验结果

### 4.1 三组对照

| 指标 | 重排（阈值 0.3） | **无重排** | **重排（阈值 -10）** |
| --- | --- | --- | --- |
| precision | 0.9688 | 1.0000 | **1.0000** |
| recall | 0.9688 | 1.0000 | **1.0000** |
| ndcg@3 | 0.9688 | 1.0000 | **1.0000** |
| ndcg@10 | 0.9688 | 1.0000 | **1.0000** |
| mrr | 0.9688 | 1.0000 | **1.0000** |
| map | 0.9688 | 1.0000 | **1.0000** |
| bleu-1 | 0.2851 | 0.3307 | **0.3349** |
| bleu-4 | — | — | **0.1963** |
| rouge-1 | 0.4281 | 0.4897 | **0.5070** |
| rouge-L | 0.4043 | 0.4664 | **0.4880** |

### 4.2 结论

**最优配置是「重排 + 放宽阈值」**：检索指标满分，生成指标全面高于无重排。

| 对比 | 检索 | rouge-1 |
| --- | --- | --- |
| 重排（阈值 -10） vs 无重排 | 持平（都满分） | **+3.5%**（0.4897 → 0.5070） |
| 重排（阈值 -10） vs 阈值 0.3 | **+3.2%** | **+18.4%**（0.4281 → 0.5070） |

## 五、关键发现：默认阈值把重排的价值掩盖了 ★

### 5.1 现象：加重排后指标反而下降

初次评测时，开启重排后 precision 从 1.0 掉到 0.9688（32 题中 1 题**检索全项 0 分**），
生成指标也同步下降。直觉上会得出"重排无用甚至有害"的结论。

> **⚠️ 重要修正**：那 1 题的 0 分后来查明是**评测框架的假阴性**——
> 该题的检索与生成实际都正确（模型答出了"一次性授权、报价需评估、通常 30 万元起"并带引用），
> 是评测框架用"字符完全包含"映射分块与标注段落时匹配失败。
> 详细分析见 [bad-cases.md](bad-cases.md) 案例 1。
> 也就是说：**本节讨论的阈值问题真实存在且已修复；但那 1 题的 0 分不能作为阈值问题的证据。**

### 5.2 定位过程

**第一步：看重排的实际打分**，而不是只看聚合指标。

```
stage=Rerank action=top_score ... rank=1 score= 6.6088   ← 正确段落
stage=Rerank action=top_score ... rank=2 score=-0.9100
stage=Rerank action=top_score ... rank=3 score=-0.9803
stage=Rerank action=top_score ... rank=4 score=-3.4015
```

**重排本身工作得非常好**——正确段落 6.61 分，其余全部为负，断崖式区分。
所以问题不在模型排序能力。

**第二步：看过滤阶段**。

```
stage=Rerank action=threshold threshold=0.3
stage=Rerank action=output    filtered_cnt=1
```

21 个候选，经阈值 0.3 过滤后**只剩 1 条**。

### 5.3 根因

**`bge-reranker-v2-m3` 输出的是原始 logits（范围约 -10 ~ +10），不是 0~1 归一化分数。**
而默认阈值 `0.3` 是按归一化分数设的。用 0.3 去卡 logits，等价于"只保留排名第一且分数为正的那条"：

- 32 题中 31 题的 top-1 恰好是标注答案 → 全部满分
- 1 题重排的 top-1 是另一个语义相近的段落 → 标注答案被阈值滤掉 → 该题全项 0 分

**这是配置与模型不匹配的问题，不是模型能力问题。**

### 5.4 验证：放宽阈值

把 `conversation.rerank_threshold` 从 `0.3` 改为 `-10`（保留全部候选，只让重排决定顺序）：

| | 阈值 0.3 | 阈值 -10 |
| --- | --- | --- |
| 检索指标 | 0.9688 | **1.0000** |
| rouge-1 | 0.4281 | **0.5070** |

检索回到满分，**生成指标还提升了 18.4%**——因为重排后的正确段落排在了最前，同时保留了必要的上下文。

### 5.5 教训

> **换重排模型必须重新校准阈值——不同模型的分数尺度完全不同。**
> 更一般的：**评测指标下降时，不要直接接受结论，要去看链路中间环节的实际输出。**
> 这次如果只看聚合指标，会得出"重排有害"的错误结论，然后把一个有价值的组件关掉。

## 六、诚实说明：本评测的局限

| 局限 | 说明 |
| --- | --- |
| **语料规模小** | 20 段落 / 32 题。指标已能区分配置差异，但不能代表生产级大语料（万级分块）的表现 |
| **单标注** | 每题仅 1 个相关段落，由一人标注，未做多人一致性校验 |
| **BLEU / ROUGE 不等于事实一致性** | 这两个指标衡量**字面重合度**。生成分数高说明措辞接近参考答案，**不能证明没有幻觉**。真实防幻觉依赖引用覆盖率 + 人工抽检 |
| **无多跳问题** | 当前问题均为单跳（答案在单一段落内）。跨段落推理的题目未覆盖 |
| **相关性阈值未做扫描** | 本次只对比了 0.3 与 -10 两个点，未做系统性的阈值扫描 |
| **评测框架存在已知假阴性** | 分块↔标注段落用"字符完全包含"匹配，格式改写即失效（见 bad-cases.md 案例 1）|

### 下一步可做的改进

1. 扩充语料到数千分块，加入更难的反例
2. 做**阈值扫描**（-10 到 +7 取多个点），画指标曲线找最优点
3. 增加多跳问题与"知识库未覆盖"类问题（测拒绝回答能力）
4. 引入引用覆盖率与人工抽检，弥补 BLEU/ROUGE 的不足
5. **修复评测框架的分块匹配逻辑**（改用分块溯源 ID 或模糊匹配），消除假阴性
6. **补充"知识库未覆盖"类问题**，让拒答能力可被衡量

## 七、复现步骤

```bash
# 1. 生成评测集（需要 pyarrow）
python3 docs/evidence/make_eval_dataset.py

# 2. 替换容器内的评测数据集（先备份原版）
docker exec knowence-app sh -c 'mkdir -p /app/dataset/backup && cp /app/dataset/samples/*.parquet /app/dataset/backup/'
for f in corpus queries answers qrels qas; do
  docker cp docs/evidence/dataset/$f.parquet knowence-app:/app/dataset/samples/$f.parquet
done
docker exec -u root knowence-app chown -R appuser:appuser /app/dataset/samples

# 3. 触发评测（需 Admin 身份）
curl -X POST http://localhost:8081/api/v1/evaluation \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"dataset_id":"knowence-policy-v2","knowledge_base_id":"<KB_ID>",
       "chat_id":"<CHAT_MODEL_ID>","rerank_id":"<RERANK_MODEL_ID>"}'

# 4. 取结果
curl "http://localhost:8081/api/v1/evaluation?task_id=<TASK_ID>" -H "Authorization: Bearer $TOKEN"
```

> **注意**：评测框架会以传入的知识库为**模板新建一个临时知识库**，评测结束后删除的是那个临时的，
> 原有知识库数据不受影响（源码 `internal/application/service/evaluation.go` 已确认）。
