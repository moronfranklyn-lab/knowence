# 部署实录（本地私有化）

> 记录知微 Knowence 在本机跑通完整链路的过程、真实架构、以及踩过的坑。
> 环境：macOS（Apple Silicon）+ Docker Desktop。日期：2026-09-29。

## 一、最终架构（4 个容器）

```
浏览器 → knowence-ui :8081 ──nginx 反代 /api/──→ knowence-app :8080
                                                    ├── knowence-db (ParadeDB/PostgreSQL)
                                                    │     ├── 元数据 + chunks + 向量（pgvector）
                                                    │     └── 关键词全文检索（pg_search / BM25）
                                                    └── knowence-embed (llama.cpp server)
                                                          └── bge-m3-FP16.gguf（本地向量，1024 维）
```

| 容器 | 镜像 | 角色 |
| --- | --- | --- |
| knowence-ui | wechatopenai/weknora-ui:v0.8.2 | 前端静态站 + nginx 反代 |
| knowence-app | wechatopenai/weknora-app:v0.8.2 | 业务后端（Go），含 RAG/Agent 管线 |
| knowence-db | paradedb/paradedb:v0.22.6-pg17 | 元数据 + 向量 + BM25 全文检索 |
| knowence-embed | llama.cpp:server | 本地向量化服务（OpenAI 兼容 `/v1/embeddings`） |

**模型分工**：对话模型走云端 API（DeepSeek）；**向量化留在本机**——文档内容在向量化环节不出机器。这是"数据不出域"与"成本可控"之间的取舍方案，也是本部署最值得讲的一个决策。

## 二、关键配置

### app 容器环境变量

```bash
DB_DRIVER=postgres
DB_HOST=postgres          # 容器网络内按服务名解析
DB_PORT=5432
DB_USER=postgres
DB_PASSWORD=<自定>
DB_NAME=WeKnora
AUTO_MIGRATE=true         # 启动自动执行迁移（本次 0 → 110）
RETRIEVE_DRIVER=postgres  # 检索后端：向量 + 关键词都走 PG
STORAGE_TYPE=local
LOCAL_STORAGE_BASE_DIR=/app/data/files
STREAM_MANAGER_TYPE=memory
JWT_SECRET=<自行生成>
SYSTEM_AES_KEY=<自行生成>
SSRF_WHITELIST_EXTRA=embed,knowence-embed   # 关键：放行内网模型地址
```

### 向量模型记录（嵌入式 bge-m3）

```
type=Embedding  source=remote  provider=generic  interface_type=openai
base_url=http://embed:8080/v1      # 指向本地 llama.cpp
embedding_parameters.dimension=1024
```

### 本地向量服务启动命令

```bash
docker run -d --name knowence-embed --network knowence-net --network-alias embed \
  -p 8080:8080 -v /path/to/models:/models:ro \
  ghcr.nju.edu.cn/ggml-org/llama.cpp:server \
  -m /models/bge-m3-FP16.gguf --embedding --pooling cls -c 8192 --host 0.0.0.0 --port 8080
```

`--pooling cls`：bge-m3 用 CLS 池化取句向量，不加会得到错误语义的向量。

## 三、踩过的坑（按教训价值排序）

### 1. 官方镜像的 SQLite 不带 FTS5 → 混合检索直接失败（最重要）

- **现象**：`RETRIEVE_DRIVER=sqlite` 时日志报 `no such module: fts5`，关键词索引表建不起来；调用混合检索接口直接返回 `FTS5 query failed`，检索完全不可用（不是降级，是报错）。
- **根因**：官方 app 镜像里编译的 SQLite 未启用 FTS5 扩展。源码 Makefile 构建 Lite 版时带 `-tags sqlite_fts5`，但发布镜像没有。
- **结论**：**要真正的"向量+关键词"混合检索，必须用 Postgres（ParadeDB）后端**，不能图省事用 SQLite。
- **面试价值**：这是"为什么生产要用专用检索组件而不是嵌入式数据库"的实证。

### 2. SSRF 防护会拦住内网模型地址

- **现象**：创建模型时被拒 —— `Base URL 未通过安全校验：... resolves to restricted IP ... private IP address`。
- **修法**：环境变量 `SSRF_WHITELIST_EXTRA=embed`（支持域名/通配/IP/CIDR）。
- **意义**：这不是 bug 而是**企业级安全设计**——平台允许用户填任意 base_url，若不拦截就能被用来探测内网服务。

### 3. docker cp 回灌数据会破坏属主，导致"能读不能写"

- **现象**：登录接口返回 token，但拿 token 调任何接口都报 `token is revoked`。
- **根因**：从宿主机 `docker cp` 进容器的数据库文件属主变成了宿主用户（uid 501），而应用进程以 `appuser`（uid 1000）运行，**只有读权限**。登录时 token 记录写不进库，校验时查不到 → 判定为"已吊销"。
- **修法**：`docker exec -u root <容器> chown -R appuser:appuser /app/data`。
- **教训**：数据卷/回灌后必须核对文件属主与运行用户是否一致。

### 4. 模型名会退役

- 本版本模型目录中 **`deepseek-chat` / `deepseek-reasoner` 已标记 2026-07-24 退役**，当前应使用 `deepseek-v4-flash`（快/省）或 `deepseek-v4-pro`（强）。填错模型名调用直接失败。

### 5. 国内网络下的下载源选择

| 资源 | 直连速度 | 可用快源 | 实测 |
| --- | --- | --- | --- |
| GitHub Release（Ollama 应用） | 超时 | gh-proxy.com | ~60-200 KB/s（仍慢） |
| Ollama 模型仓库 | ~186 KB/s | ModelScope GGUF | **10.4 MB/s** |
| Docker Hub | 超时 | docker.m.daocloud.io | 秒级响应 |
| GHCR | 慢 | ghcr.nju.edu.cn | **0.12s 响应** |
| PyPI | — | 清华镜像 | 快 |

**结论**：本地模型优先从 ModelScope 取 GGUF；镜像优先走高校/云厂商镜像源。

### 6. 向量模型一旦入库就不能换

源码中 `Cannot change embedding model when files exist`——**向量模型必须在灌入第一份文档之前定死**，之后更换会导致整个索引不可用（维度/语义空间都不兼容）。

## 五、复现步骤（最小化）

1. 建网：`docker network create knowence-net`
2. 起 ParadeDB：见上文环境变量，映射 5432
3. 起本地向量：llama.cpp + bge-m3 GGUF（`--embedding --pooling cls`）
4. 起后端：app 镜像 + 上述环境变量（务必含 `SSRF_WHITELIST_EXTRA`）
5. 起前端：ui 镜像，`APP_HOST=knowence-app` 指向后端
6. 注册账号 → 添加向量模型 → 建知识库 → 上传文档 → 检索验证
