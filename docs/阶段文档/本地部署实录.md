# 部署实录（本地私有化）

> 记录知微 Knowence 跑通完整链路的过程、真实架构、以及踩过的坑。
> 环境：macOS（Apple Silicon，平台节点）+ Docker Desktop + Windows 10 / RTX 4060 8GB（推理节点）。
> 日期：2026-09-29 起，2026-10-01 补齐本地对话模型与重排。

## 一、最终架构（平台节点 + 推理节点分离）

```
        Mac（平台节点）                          Windows（推理节点）
┌──────────────────────────────┐        ┌──────────────────────────┐
│ ① 混合检索                    │        │  RTX 4060 8GB            │
│    向量(pgvector) + BM25      │        │  Qwen2.5-7B-Instruct     │
│ ② Rerank 重排                 │        │  Q4_K_M · 100% GPU       │
│    bge-reranker-v2-m3 FP16   │───────►│  实测 48.9 tok/s          │
│ ③ 本地向量化 bge-m3（1024维） │ 局域网 │                          │
│ ④ 引用回填 + 审计             │◄───────│  生成答案 + 引用标记      │
└──────────────────────────────┘        └──────────────────────────┘
        文档内容全程不出内网
```

**局域网地址**：平台节点 `<平台节点IP>`，推理节点 `<推理节点IP>:11434`（Ollama OpenAI 兼容接口）。
实测环境使用 `192.168.1.x` 网段，实际部署请替换为你的内网地址。

```
浏览器 → knowence-ui :8081 ──nginx 反代 /api/──→ knowence-app :8080
                                                    ├── knowence-db (ParadeDB/PostgreSQL)
                                                    │     ├── 元数据 + chunks + 向量（pgvector）
                                                    │     └── 关键词全文检索（pg_search / BM25）
                                                    ├── knowence-embed (llama.cpp server)
                                                    │     └── bge-m3-FP16.gguf（本地向量，1024 维）
                                                    └── knowence-rerank (llama.cpp server, --rerank)
                                                          └── bge-reranker-v2-m3-FP16.gguf
```

| 组件 | 镜像/形态 | 角色 |
| --- | --- | --- |
| knowence-ui | wechatopenai/weknora-ui:v0.8.2 | 前端静态站 + nginx 反代 |
| knowence-app | wechatopenai/weknora-app:v0.8.2 | 业务后端（Go），含 RAG/Agent 管线 |
| knowence-db | paradedb/paradedb:v0.22.6-pg17 | 元数据 + 向量 + BM25 全文检索 |
| knowence-embed | llama.cpp:server | 本地向量化（OpenAI 兼容 `/v1/embeddings`） |
| knowence-rerank | llama.cpp:server `--rerank` | 本地重排（Cohere 兼容 `/v1/rerank`） |
| 推理节点 | Windows + Ollama 0.35.0 | 本地对话模型（OpenAI 兼容 `/v1/chat/completions`） |

### 为什么推理与平台分离

Mac 只有一块集成显卡，**Docker Desktop 在 macOS 上无法把 GPU 透传进容器**，容器内只能纯 CPU 推理——实测 3B 模型只有 **2.0 tok/s**，不可用。
把对话模型放到一台带独显的 Windows 机器上，Mac 只做平台与检索，两端通过局域网调用。

这同时**贴近真实企业架构**：推理节点（吃 GPU）与平台节点（吃 IO/存储）职责分离、可独立扩容、可独立替换。

**模型分工**：向量化、重排、对话生成**全部本地**——文档内容在整条链路上不出内网。这是"数据不出域"与"成本可控"之间取舍后的最终形态。

```bash
docker run -d --name knowence-embed --network knowence-net --network-alias embed \
  -p 8080:8080 -v /path/to/models:/models:ro \
  ghcr.nju.edu.cn/ggml-org/llama.cpp:server \
```

## 三、踩过的坑（按教训价值排序）

### 1. 官方镜像的 SQLite 不带 FTS5 → 混合检索直接失败（最重要）

- **现象**：`RETRIEVE_DRIVER=sqlite` 时日志报 `no such module: fts5`，关键词索引表建不起来；调用混合检索接口直接返回 `FTS5 query failed`，检索完全不可用（不是降级，是报错）。
- **根因**：官方 app 镜像里编译的 SQLite 未启用 FTS5 扩展。源码 Makefile 构建 Lite 版时带 `-tags sqlite_fts5`，但发布镜像没有。
- **结论**：**要真正的"向量+关键词"混合检索，必须用 Postgres（ParadeDB）后端**，不能图省事用 SQLite。
- **面试价值**：这是"为什么生产要用专用检索组件而不是嵌入式数据库"的实证。

### 2. SSRF 防护会拦住内网模型地址

- **现象**：创建模型时被拒 —— `Base URL 未通过安全校验：... resolves to restricted IP ... private IP address`。
- **修法**：环境变量 `SSRF_WHITELIST_EXTRA=embed`（支持域名/通配/IP/CIDR）。
- **意义**：这不是 bug 而是**企业级安全设计**——平台允许用户填任意 base_url，若不拦截就能被用来探测内网服务。

### 3. docker cp 回灌数据会破坏属主，导致"能读不能写"

- **现象**：登录接口返回 token，但拿 token 调任何接口都报 `token is revoked`。
- **根因**：从宿主机 `docker cp` 进容器的数据库文件属主变成了宿主用户（uid 501），而应用进程以 `appuser`（uid 1000）运行，**只有读权限**。登录时 token 记录写不进库，校验时查不到 → 判定为"已吊销"。
- **修法**：`docker exec -u root <容器> chown -R appuser:appuser /app/data`。
- **教训**：数据卷/回灌后必须核对文件属主与运行用户是否一致。

### 4. 模型名会退役

- 本版本模型目录中 **`deepseek-chat` / `deepseek-reasoner` 已标记 2026-07-24 退役**，当前应使用 `deepseek-v4-flash`（快/省）或 `deepseek-v4-pro`（强）。填错模型名调用直接失败。

### 5. 国内网络下的下载源选择

| 资源 | 直连速度 | 可用快源 | 实测 |
| --- | --- | --- | --- |
| GitHub Release（Ollama 应用） | 超时 | gh-proxy.com | ~60-200 KB/s（仍慢） |
| Ollama 模型仓库 | ~186 KB/s | ModelScope GGUF | **10.4 MB/s** |
| Docker Hub | 超时 | docker.m.daocloud.io | 秒级响应 |
| GHCR | 慢 | ghcr.nju.edu.cn | **0.12s 响应** |
| PyPI | — | 清华镜像 | 快 |

**结论**：本地模型优先从 ModelScope 取 GGUF；镜像优先走高校/云厂商镜像源。

### 6. 向量模型一旦入库就不能换

源码中 `Cannot change embedding model when files exist`——**向量模型必须在灌入第一份文档之前定死**，之后更换会导致整个索引不可用（维度/语义空间都不兼容）。

### 7. Docker 共享挂载让 mmap 退化成逐次读盘（性能差 9 倍）★

- **现象**：把 GGUF 模型放在宿主机目录、以 bind mount 挂进容器，3B 模型只有 **2.0 tok/s**，加载耗时 **264 秒**。
- **根因**：llama.cpp 用 **mmap** 读取模型权重，而 macOS ↔ Docker VM 之间是 VirtioFS 共享层，mmap 页访问走慢路径，**每个 token 生成都在跨层读权重**。
- **修法**：把模型文件复制进 **Docker 原生卷**（`docker volume`）后再挂载。
- **实测效果**：

| 指标 | 共享挂载 | 原生卷 | 提升 |
| --- | --- | --- | --- |
| 模型加载 | 264 s | 105 s | 2.5× |
| **推理速度** | **2.0 tok/s** | **18.7 tok/s** | **9.4×** |

- **教训**：**容器里跑大模型，模型文件必须落在容器原生文件系统上。** 这条对向量模型、重排模型同样适用。

### 8. Windows 自带 OpenSSH 装不全，sshd 静默失败

- **现象**：`Add-WindowsCapability` 显示 `OpenSSH.Server` 已安装，但 `Start-Service sshd` 只给一句"无法启动计算机上的服务"，**不写事件日志、不给错误码**；手工跑 `sshd.exe -ddd` 也无任何输出。
- **两个叠加根因**：
  1. **配置文件缺失**：`C:\ProgramData\ssh\sshd_config` 不存在（用 `Add-WindowsCapability` 安装时有时不生成），需从 `C:\Windows\System32\OpenSSH\sshd_config_default` 拷贝；
  2. **二进制损坏**：修好配置后仍失败，直接运行报 **"无法定位程序输入点…于动态链接库"**——组件源不完整导致 DLL 入口点缺失，**这套内置 OpenSSH 已不可用**。
- **另一个坑**：Windows 的 OpenSSH 有**两个可能位置**（`System32\OpenSSH` 与 `ProgramFiles\OpenSSH`），取决于安装方式；只按一个路径找会白折腾。
- **最终方案**：放弃系统 SSH，改用 **HTTP 轮询通道**（Mac 端下发命令 → Windows 执行 → 回传结果），不依赖任何系统组件。
- **教训**：**远程执行通道要给每条命令设硬超时**——否则一条阻塞命令（例如等 GUI 安装器返回）就能把整条通道冻死，且没有任何反馈。

### 9. PowerShell 5.1 读 UTF-8 无 BOM 脚本会按 ANSI 解码

- **现象**：`.ps1` 脚本里带中文，执行报**语法错误**（`Missing closing '}'`），而花括号明明是配平的。
- **根因**：PowerShell 5.1 读 `.ps1` 时，若文件是 **UTF-8 无 BOM**，会按系统 ANSI 代码页（中文 Windows = GBK）解码。中文字符的 UTF-8 字节被误读后可能"吃掉"紧随其后的字符——**包括 `}` 和引号**。
- **修法**（从稳到不稳）：① 脚本内不写非 ASCII 字符；② 存为 UTF-8 **带 BOM**；③ 显式设置 `[Console]::OutputEncoding`（治标不治本）。
- **教训**：**跨平台脚本的第一原则是纯 ASCII**，中文只放在输出层。

### 10. 问答路径漏传 rerank 模型 ID，重排被静默跳过 ★

- **现象**：数据库 `tenants.retrieval_config` 里 `rerank_model_id` 已正确写入，模型也注册成功，但检索质量没变化。
- **定位**：日志里一行关键信息——
  ```
  [PIPELINE] stage=Rerank action=input candidate_cnt=3 rerank_model=""
  [PIPELINE] stage=Rerank action=skip reason="empty_model_id"
  ```
  **重排被静默跳过，不报错。**
- **根因**：项目里有**两条检索路径**：
  - `SearchKnowledge` 会从租户 `RetrievalConfig` 读 `RerankModelID`（并有"自动选第一个 rerank 模型"的兜底）；
  - 而问答路径 `KnowledgeQAByEvent` 构造请求时设了 `RerankTopK` / `RerankThreshold`，**唯独漏了 `RerankModelID`**。
- **修法（不改代码）**：改走 **Agent 路径**——`session_agent_qa.go` 从 `agent.Config.RerankModelID` 读取，并且**当 Agent 启用了知识检索工具时强制要求配置**（源码注释说明这是有意设计：把配置放在用户真正编辑的地方，避免"租户设置 vs Agent 设置"之间互相猜）。创建一个配好 `rerank_model_id` 的 Agent，请求带上 `agent_enabled + agent_id` 即可。
- **验证**：重排服务调用计数从 10 → 13（3 个候选文档被重排），端到端 8.8s，答案带引用。
- **教训**：**同一功能在系统里有多条实现路径时，配置能生效≠所有入口都能生效。** 定位这类问题不能只看配置层，要看**执行路径的日志**。而且——**静默跳过比报错更危险**。

### 11. 重排默认阈值与该模型的分数尺度不匹配，把正确答案滤掉了 ★★

- **现象**：开启重排后，评测 precision 从 1.0 掉到 **0.9688**（32 题中 1 题全项 0 分），生成指标同步下降。直觉结论是"重排有害"。
- **定位第一步——看重排的实际打分**（不要只看聚合指标）：
  ```
  rank=1 score= 6.6088   ← 正确段落
  rank=2 score=-0.9100
  rank=3 score=-0.9803
  ```
  **重排本身工作得极好**，正确段落断崖式领先。问题不在模型排序能力。
- **定位第二步——看过滤阶段**：
  ```
  stage=Rerank action=threshold threshold=0.3
  stage=Rerank action=output    filtered_cnt=1
  ```
  21 个候选经阈值 0.3 过滤后只剩 1 条。
- **根因**：`bge-reranker-v2-m3` 输出**原始 logits（约 -10 ~ +10）**，不是 0~1 归一化分数；
  而默认阈值 `0.3` 是按归一化分数设的。用 0.3 卡 logits 等价于"只保留排名第一且为正的那条"——
  一旦 top-1 不是标注答案，该题就彻底丢分。
- **修法（不改代码）**：把 `conversation.rerank_threshold` 从 `0.3` 改为 `-10`（保留全部候选，只让重排决定顺序）。
- **效果**：

  | 配置 | 检索指标 | rouge-1 |
  | --- | --- | --- |
  | 重排，阈值 0.3 | 0.9688 | 0.4281 |
  | 无重排 | 1.0000 | 0.4897 |
  | **重排，阈值 -10** | **1.0000** | **0.5070** |

  检索回满分，**生成指标提升 18.4%**。完整报告见 [docs/evidence/评测报告.md](../evidence/评测报告.md)。

- **教训**：
  > **换重排模型必须重新校准阈值——不同模型的分数尺度完全不同。**
  > 更一般的一条：**指标下降时不要直接接受结论，要去看链路中间环节的实际输出。**
  > 这次若只看聚合数字，就会误判"重排有害"，从而把一个真正有价值的组件关掉。

## 五、复现步骤（最小化）

1. 建网：`docker network create knowence-net`
2. 起 ParadeDB：见上文环境变量，映射 5432
3. 起本地向量：llama.cpp + bge-m3 GGUF（`--embedding --pooling cls`），**模型文件放 Docker 原生卷**
4. 起本地重排：llama.cpp + bge-reranker-v2-m3 GGUF（`--rerank`），同样放原生卷
5. 起后端：app 镜像 + 上述环境变量（务必含 `SSRF_WHITELIST_EXTRA=embed,rerank,<推理节点IP>`）
6. 起前端：ui 镜像，`APP_HOST=knowence-app` 指向后端
7. 推理节点：Windows 装 Ollama → 设 `OLLAMA_HOST=0.0.0.0:11434` → 放行防火墙 → 用 ModelScope 的 GGUF `ollama create`
8. 注册账号 → 添加向量模型 → **添加重排模型** → 建知识库 → 上传文档
9. **配置 Agent 并把 `rerank_model_id` 写进 Agent**（问答路径不会读租户级配置，见坑 10）
10. 检索验证 → 问答验证 → 确认重排服务日志有调用
